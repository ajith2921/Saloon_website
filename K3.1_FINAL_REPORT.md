# K3.1 FINAL REPORT

## 1. K3.1 Status
**COMPLETED** (Discovery and Audit Phase)

## 2. Existing Subscription Architecture
**NON-EXISTENT**. 
The repository currently contains **no** subscription tables, columns, or relations in the Supabase schema. Subscriptions are entirely a manual, off-platform process where super-admins communicate with salon owners via email (`team@queuecut.com`).

## 3. Existing Plans Architecture
**HARDCODED (Frontend Only)**. 
Plans (e.g., Free, Essential, Professional) only exist as hardcoded JSON objects inside `salon-frontend/src/pages/superadmin/Subscriptions.jsx`. There is no `plans` table in the database, and the backend has no concept of plans or limits.

## 4. Existing Billing Provider Status
**NON-EXISTENT**.
There is no integration with Stripe, Razorpay, or any other payment gateway. No SDKs are installed, no webhook endpoints exist, and no checkout sessions are generated.

## 5. Database Findings
- **No tables** exist for `subscriptions`, `plans`, `invoices`, or `payments`.
- Existing `salons` table contains no fields representing a subscription ID, plan tier, or billing status.
- **Database is fundamentally secure** regarding billing simply because billing state does not exist in the database.

## 6. RLS Findings
N/A for subscriptions (no tables exist). Existing RLS successfully isolates salons and tokens (as verified by the regression suite).

## 7. API Findings
- **No backend routers** or endpoints exist for billing or subscriptions.
- The `platform_revenue_month` in `super_admin.py` is calculated purely by summing the `price` of completed `tokens -> services`, not through a billing gateway.
- No endpoints exist that would improperly trust client-side pricing or plan logic.

## 8. Frontend Findings
- `Subscriptions.jsx` (Super Admin) displays hardcoded plans.
- The UI explicitly states: *"Automated subscription management and payment gateway integration is under development."*
- There are no customer-facing or salon-owner-facing billing screens. The frontend does not expose fake or insecure billing UI.

## 11. Subscription State Model (Proposed for K3.2)
Since it does not exist, K3.2 must implement the following authoritative states:
- `trialing`: Active during initial grace period.
- `active`: Paid and current.
- `past_due`: Payment failed, in grace period.
- `canceled`: User canceled, active until end of billing cycle.
- `expired`: Cycle ended, limits restricted.

## 12. Entitlement Model (Proposed for K3.2)
Currently, a salon can add unlimited workers and services. K3.2 must introduce a `plan_limits` structure that the backend enforces (e.g., rejecting a `POST /workers` request if `current_workers >= plan_limit`).

## 13. Billing Provider Readiness
**READY FOR GROUND-UP INTEGRATION**.
The system has clean, robust authentication (Supabase Auth) and tenant isolation (Salon ID), meaning a billing provider (like Stripe) can be integrated safely by associating a `stripe_customer_id` with a `salons.id`. 
Requirements for K3.2:
- Add `stripe_customer_id` and `stripe_subscription_id` to `salons` or a new `subscriptions` table.
- Implement secure webhook verification in FastAPI.

## 22. Remaining Risks
The primary risk moving into K3.2 will be **Trust Boundaries**. The frontend MUST NOT be allowed to dictate which plan a salon is on by sending `plan_id: "premium"` during normal updates. Webhooks must be the sole authority for state changes.

## 23. Recommended K3.2 Scope
1. **Database Migration**: Create `plans` and `subscriptions` tables with strict RLS (Owners can READ their own, System/SuperAdmin can UPDATE).
2. **Backend Webhooks**: Implement FastAPI Stripe webhook listeners with signature verification.
3. **Checkout Flow**: Implement a backend route to generate Stripe Checkout Sessions.
4. **Enforcement**: Update existing backend endpoints (Workers, Services, Queue) to check subscription limits before allowing mutations.
