## 3. Plan Architecture

Plans are now structurally defined in the database (`subscription_plans`). The pricing, currency, billing intervals, feature set, and limits (`max_workers`, `max_services`, `max_monthly_tokens`) are authoritative at the database level. 

## 4. Subscription Architecture

Subscriptions (`subscriptions` table) securely map a `salon_id` to a `plan_id` with state constraints. Historical subscriptions are preserved by never deleting plans (`ON DELETE RESTRICT`) and by retaining cancelled subscriptions.

## 5. Subscription State Model

The state is governed by an ENUM (`subscription_status`): `trialing`, `active`, `past_due`, `cancelled`, `expired`, `suspended`. The frontend has no endpoints to mutate this state. State changes are strictly reserved for the future backend payment webhooks or secure admin interventions.

## 6. Entitlement Architecture

Limits are derived from the database join of a salon's active subscription to its plan (`GET /api/subscriptions/entitlements`). The frontend has been purged of hardcoded plan matrices.

## 7. RLS Architecture

- **subscription_plans**: Anyone can SELECT active plans. Super admins can ALL.
- **subscriptions**: Salon owners can SELECT their own subscriptions via tenant isolation. Super admins can ALL. No frontend-facing INSERT/UPDATE endpoints exist.

## 8. Backend Authorization

All endpoints in `subscriptions.py` enforce strict RBAC via `require_role('salon_owner')` or `require_role('super_admin')`. Tenant isolation is performed by directly pulling `db_salon_id` from the trusted JWT and Profile context, entirely ignoring client-provided payloads.

## 11. Database Constraints

- `ON DELETE RESTRICT` on `plan_id` to prevent breaking active subscriptions if a plan is removed.
- `ON DELETE CASCADE` on `salon_id` to clean up subscriptions if a salon is deleted.
- Partial Unique Index enforces exactly ONE active/trialing/past_due subscription per salon.
